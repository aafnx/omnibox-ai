# Подключение клиентов к API

OmniBox AI отдаёт OpenAI-совместимый API по пути `/v1` на порту панели. Запросы идут к **запущенному в панели движку**: работает один движок и одна модель. Запрос к API не запускает сервер и не загружает модель — это делается в панели.

## Настройки в Jan, Pi, Open WebUI

| Поле | Значение |
|---|---|
| Провайдер | OpenAI-compatible / Custom OpenAI |
| Base URL | `https://llm.fnx.red/v1` через NAS или `http://<IPv4 ПК>:8800/v1` в локальной сети |
| API key | свой ключ для каждого клиента: панель → Подключение → «API-ключи клиентов» → «Создать ключ» (ключ установки называется «Основной») |
| Model | настоящее имя модели: имя GGUF без расширения для PrismML (например, `ornith-27b-Q4_K_M`) или имя Ollama (`qwen3:8b`) |

`/v1/models` показывает только загруженную модель. Запрос с именем другой модели получает ошибку 409 с просьбой выбрать модель в панели.

Поддерживаются `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/responses` и `/v1/models`, потоковая передача (SSE) и инструменты (tools).

## Очередь запросов

Генерация выполняется одна за раз. Пока она идёт, следующие запросы ждут в очереди — так служебные запросы Open WebUI (заголовки, теги) не получают ошибок.

| Настройка (панель → Подключение) | По умолчанию | |
|---|---|---|
| Очередь запросов | 4 | 0 — сразу ответ 409, как раньше |
| Ожидание в очереди | 60 с | затем ответ 503 |

Переполненная очередь отвечает 429 с `Retry-After` (клиенты OpenAI повторяют такой запрос сами). Остановка, выгрузка или смена модели и настроек сразу отменяют ожидающие запросы (503): они никогда не выполнятся на другой модели. Остановка прерывает и текущую генерацию.

## Ключ

Ключи хранятся только в виде SHA256 и показываются один раз. У каждого клиента может быть свой ключ с именем: в панели видно, когда он использовался и сколько токенов потратил, и его можно отозвать, не трогая остальные. `ai key new` и «Заменить все ключи одним новым» отзывают все ключи сразу — на случай утечки. Работа без ключа разрешена (снимите флажок «Требовать API key»), но только в закрытой сети.

## Reverse proxy на Synology NAS

Схема: клиент → `https://llm.fnx.red` (DNS только в LAN и WireGuard) → NAS `192.168.1.10` (TLS) → `http://192.168.1.77:8800` → OmniBox → движок на `127.0.0.1:8801/8802`.

Правило обратного прокси (Панель управления → Портал входа → Дополнительно → Обратный прокси):

| Вкладка | Значение |
|---|---|
| Источник | HTTPS, `llm.fnx.red`, 443, HSTS |
| Профиль доступа | «Разрешить» `192.168.1.0/24` и подсеть WireGuard, остальным «Запретить» |
| Место назначения | HTTP, `192.168.1.77`, **8800** |
| Пользовательский заголовок | только `X-Forwarded-Proto: https`, `X-Forwarded-Host: llm.fnx.red`, `X-Forwarded-For: $remote_addr`; заголовки `Upgrade`, `Connection` и `Authorization` удалите |
| Дополнительно | соединение 60 с, отправка и чтение 1800 с, HTTP 1.1 |

Установщик по умолчанию задаёт HTTPS-адрес `https://llm.fnx.red` и IP NAS `192.168.1.10`; изменить или убрать их можно в панели («Подключение» → настройки API, поля «HTTPS-адрес через NAS» и «IP NAS»): заголовки `X-Forwarded-*` и имя `llm.fnx.red` в заголовке `Host` (NAS передаёт его без изменений) принимаются только от него. Если NAS дописывает цепочку в `X-Forwarded-For`, панель берёт последний адрес — тот, с которого к NAS пришёл клиент. Входы в панель (адрес, результат) записываются в `logs/panel.log`. Потоковые ответы приходят с `X-Accel-Buffering: no`, поэтому NAS не копит токены.
