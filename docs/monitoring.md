# Мониторинг и журнал запросов

## Ресурсы

Обзор показывает CPU, занятую/общую RAM, нагрузку GPU, VRAM, температуру GPU и мощность GPU. CPU/RAM читаются из локального Windows CIM, GPU — из `nvidia-smi`. Температура CPU исключена, дополнительное ПО не нужно. Вентиляторы GPU: `fan.speed` из nvidia-smi, в процентах заданной скорости; это не измерение RPM. N/A показывается как «—». RAM/VRAM размещения модели не равны всей занятой системной памяти.

Видимая вкладка запрашивает статус/активность примерно каждые 3 секунды, пока работает движок или идёт операция. Системный сэмплер выполняется отдельным ThreadJob, максимум один одновременно, и не блокирует управление. При остановленных движках, спящей Bonsai или выгруженной Ollama автоматического опроса ресурсов нет. При скрытой/закрытой вкладке запросов нет; уже запущенный краткий сэмплер может завершиться. В idle нет собственного фонового таймера, пробуждающего ПК. Когда постоянного опроса нет, панель делает один снимок ресурсов по действию пользователя: при входе, при возврате на вкладку и по кнопке «Обновить данные». Снимок остаётся на экране с временем замера, а над карточками указано, почему постоянный опрос выключен. Снимок выполняется тем же ThreadJob и не запускает периодический опрос (`/api/telemetry?once=1`).

## Прогресс и текущая активность

Запуск/загрузка отображаются индикатором ожидания и прошедшим временем. У движков нет общего достоверного процента загрузки, поэтому индикатор не рисует выдуманные 0–100%. Входящий `prompt_progress` PrismML показывает реальные обработанные/общие токены входа.

Карточка текущего сеанса показывает работающий движок, выбранную модель, выполнение запроса и input/output/total. Во время потока шлюз запрашивает `stream_options.include_usage=true`. Для PrismML дополнительно передаются `timings_per_token=true` и `return_progress=true`; при активной генерации доступны счётчики `/slots`. Ответы передаются клиенту сразу. Служебные поля остаются совместимыми с поддерживающим их runtime.

Некоторые движки отдают точный input/output только в конце ответа. До появления счётчика отображается «—». Количество SSE-фрагментов не считается количеством токенов. Используются только числовые поля движка; информация не оценивается по длине текста.

**Контекст запроса** — input + output по счётчикам движка. Остаток — max(0, лимит контекста − контекст запроса). Это не измерение физической занятости KV-кеша и не накопленный контекст всех сообщений сеанса. При cache reuse/context shifting эти величины могут отличаться. Отдельно показан лимит работающей модели. Сохранённый, но не применённый новый контекст не выдаётся за действующий.

## Метаданные запросов

Раздел «Журналы» показывает до 200 последних запросов и итоги сеансов. Файл: `C:\tools\ai\logs\requests\requests.jsonl`. Записываются только:

- ID запроса/сеанса, движок, выбранная модель, фиксированный маршрут API;
- время начала/окончания UTC, длительность, HTTP-статус и завершение/ошибка;
- input/output/total, лимит и счётчики контекста, доступный числовой прогресс.

Messages, prompt, content, ответы, tools/arguments, API key, cookie, IP клиента и исходный идентификатор клиента не записываются. Журнал создаётся после допуска запроса к выбранной модели; ошибки авторизации/валидации до допуска не являются генерацией. Запросы напрямую к native API, `ollama run`, сторонние программы и журналы самого runtime не перехватываются этим журналом.

Журнал ограничен тремя файлами примерно по 4 МиБ (`requests.jsonl`, `.1`, `.2`). Последние 500 записей и до 100 сеансов находятся в памяти, UI показывает 200. При перезапуске панели восстановление идёт из оставшихся файлов. Старые записи/итоги за пределами ротации не обещаются как бессрочная история. Ошибка записи показывается в панели, генерация из-за неё не прекращается.

## Что означает сеанс

Без идентификатора клиента запросы группируются по активной модели/движку в рамках сеанса шлюза. Смена/остановка модели через панель и обнаружение остановленного/спящего движка завершают такую группу; перезапуск панели создаёт новую группу, сохраняя старые итоги. Это **не автоматическое распознавание отдельных чатов Jan/Pi**.

Клиент, который позволяет добавлять HTTP-заголовки, может отправлять `X-Omnibox-Session: <идентификатор-чата>` до 128 символов. В журнале хранится hash идентификатора вместе с моделью/движком, а не исходная строка. Запросы с этим заголовком группируются отдельно. Использование заголовка необязательно.

Итоги сеанса суммируют известные счётчики завершённых/прерванных запросов. Столбец «без usage» показывает число запросов с неполными счётчиками; отсутствие данных не заменяется достоверным нулём. При прерывании потока могут сохраниться только счётчики, успевшие прийти.

## Одна модель

Управляемый запуск всегда останавливает остальные настроенные движки, включая старую конфигурацию `exclusive:false`. PrismML получает `-np 1`, Ollama — `OLLAMA_MAX_LOADED_MODELS=1` и `OLLAMA_NUM_PARALLEL=1`. При явном выборе новой модели Ollama предыдущие выгружаются перед загрузкой, а её имя сохраняется в `config.json → active_model`.

Через OpenAI API разрешена только выбранная модель и одна генерация одновременно. Другой model или второй запрос получают 409; `n/best_of != 1` и переопределение `options.num_ctx` на другое значение отклоняются; контекст меняется в настройках модели. Смена/загрузка/перезапуск через панель ждут завершения генерации; остановка/выгрузка могут её прервать. API не запускает остановленный движок. `/v1/models` перечисляет только выбранную модель.

Ручной запуск служб и чужие процессы находятся вне управления OmniBox AI. Если обнаружены две настроенные активные службы или несколько загруженных Ollama-моделей, шлюз отказывается от генерации до устранения конфликта. Одна модель не гарантирует достаточную память для произвольного контекста — лимит зависит от модели/кванта/железа.

Источники: [Ollama concurrency](https://docs.ollama.com/faq), [OpenAI-compatible usage](https://docs.ollama.com/api/openai-compatibility), [PrismML server](https://github.com/PrismML-Eng/llama.cpp/blob/prism/tools/server/README.md).

## Отсчёт выгрузки и размещение

Отсчёт в карточке модели обновляется в браузере каждую секунду, без дополнительных HTTP-запросов. Во время генерации таймер показывает «после завершения запроса». Ollama предоставляет `expires_at` в `/api/ps`; новый запрос или keep_alive клиента может изменить срок. PrismML не предоставляет абсолютный срок в `/props`: знак ≈ означает оценку от старта процесса и последнего завершённого запроса через gateway. Долгая начальная загрузка и прямые обращения к native API могут сдвинуть фактическую выгрузку. Пока время неизвестно, нулевое значение не подставляется. Само ожидание таймера не запускает сервер и не пробуждает ПК.

В настройках: RAM/CPU; для PrismML также VRAM/GPU (все слои) или RAM + VRAM (явное число GPU-слоёв). Для Ollama — RAM/CPU либо автоматическое распределение. CPU-режим Ollama скрывает GPU от discovery на уровне службы, поэтому сохраняется и для OpenAI-клиентов; при возврате auto прежние маски восстанавливаются. Настройки применяются после загрузки/перезапуска. VRAM не гарантирует, что новая модель поместится: при ошибке запуска выполняется прежний откат.

Фактическое размещение Ollama читается из `size_vram`/`size` — это оценка распределённой памяти движка. PrismML: количество offloaded/total слоёв из журнала загрузки, которое runtime сохраняет без текста запросов. VRAM означает GPU-слои; вспомогательная RAM всё равно используется. Без фактических данных показывается «нет данных».

Журнал запросов и диагностические события единые для всей панели. В событиях остаётся источник строки, чтобы определить процесс при ошибке; переключателя отдельных журналов Ollama/PrismML нет.

Источники: [Ollama GPU discovery](https://github.com/ollama/ollama/blob/main/docs/gpu.mdx), [Ollama ps](https://github.com/ollama/ollama/blob/main/docs/api.md), [NVIDIA fan speed](https://docs.nvidia.com/deploy/nvidia-smi/index.html).
