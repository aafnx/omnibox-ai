# План развития OmniBox AI

Состояние на 2026-10-06, версия **0.9.4**. Документ фиксирует, что уже сделано, что нужно исправить (по приоритету) и куда развивать проект. В конце — поэтапный план реализации с критериями готовности.

## Сценарий и модель угроз

- Серверный ПК с Windows дома: движки (PrismML `llama-server`, Ollama) и панель `omnibox-ai` как Windows-службы.
- Ноутбук/телефон подключаются **извне только через WireGuard**. Внутри сети NAS выполняет reverse proxy: `https://llm.fnx.red/` → панель, `https://llm.fnx.red/v1` → OpenAI API, upstream `http://192.168.1.77:18090`.
- Из публичного интернета панель и API не доступны. Остаточный риск — скомпрометированное устройство внутри LAN/WireGuard. Поэтому меры безопасности ниже отнесены к «защите в глубину» (P2), а не к срочным.

## 1. Что уже реализовано

### Управление движками
- Два типа движков: PrismML `llama-server` (включая Bonsai PQ2) и Ollama; имена служб, порты и пути задаются в `config.json`.
- Эксклюзивность: запуск одного движка останавливает остальные; один слот PrismML (`-np 1`), одна модель и один параллельный запрос Ollama.
- Запуск/остановка/перезапуск, «Остановить все серверы», ожидание готовности API (`/health`, `/api/version`).
- Настройки запуска через XML-профиль: контекст, время простоя, GPU layers, Flash Attention, KV cache (f16/q8_0/q4_0), batch/ubatch, размещение RAM/VRAM/гибрид.
- «Сохранить на следующий запуск» или «Применить сейчас»; автоматический откат XML при неудачном запуске, `ai restore`, история с SHA256 и флагом pending.
- Системный mutex `Global\omnibox-ai-control-v1` сериализует CLI и панель.

### Собственный service runtime
- `Service.Host.exe` (C#, собирается встроенным `csc.exe`): регистрация в SCM, Job Object для дерева процессов, журналы с ротацией 3 × 4 МиБ, `runtime.json` (PID, offload слоёв на GPU).
- Миграция со старых `pwsh service.ps1` и WinSW-служб через проверенный `Win32_Service.Change`.

### Веб-панель
- Вкладки: обзор, модели, подключение, журналы, обновления; светлая/тёмная/системная тема, брендинг OMNIBOX, локальные шрифты Inter.
- Мониторинг CPU/RAM/GPU/VRAM/температур/вентиляторов только при открытой вкладке и работающем движке; без фонового опроса.
- Активность модели: текущий запрос, input/output/total токены, заполнение контекста, итоги по сеансам, журнал без содержимого запросов.
- Каталог Hugging Face: поиск GGUF-репозиториев и файлов, скачивание GGUF с проверкой заголовка и SHA256; `ollama pull` по имени.
- Отсчёт до выгрузки по простою, фактическое размещение модели (RAM/VRAM/гибрид).

### OpenAI-совместимый API
- `/v1/models`, `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/responses` на порту панели (и опционально на отдельном порту).
- Асинхронный C#-прокси (`OpenAi.Proxy.cs`): SSE со сбросом буфера, лимит тела 8 МиБ, таймаут 30 мин, только loopback-upstream, без редиректов.
- API key (SHA256-хэш, сравнение за постоянное время), отдельный `upstream_api_key` для движка.
- Принимается только выбранная модель; контекст и размещение фиксируются панелью (`num_ctx`, `num_gpu`).
- Сбор usage из JSON/SSE, принудительный `include_usage` для стриминга.

### Безопасность панели
- Пароль PBKDF2-SHA256 (210 000 итераций), блокировка IP после 6 ошибок на 5 минут.
- Сессии 8 ч, cookie `HttpOnly; SameSite=Strict; Secure` (за proxy), CSRF-токен, проверка Origin и Host.
- Доверие `X-Forwarded-*` только от перечисленных IP NAS; CSP, `X-Frame-Options`, `nosniff`.
- Фиксированные маршруты, нет исполнения команд и чтения произвольных файлов через API.

### Установка и обновления
- Единый установщик `dist/install-omnibox-ai.ps1` со встроенным пакетом и SHA256, мастер настройки, ACL и Firewall.
- `ai update` через `gh`; обновление из веб-панели (вход gh по коду или разовый токен, DPAPI-хранение, временная служба-worker, снимок и восстановление при сбое).

### CLI
- `ai start/stop/restart/context/restore/status/power/logs/endpoint/config/update/access/password reset/version/help`, сквозные команды Ollama.

### Тесты
- `tests/test.ps1` (core), `update_test.ps1`, `install_flow_test.ps1`, `native_host_test.ps1`, `http_test.py` (настоящий HTTP-сервер), `web_test.cjs` (поведение UI с DOM-адаптером).
- Реальные SCM, ACL, Firewall и DPAPI проверяются вручную на серверном ПК.

## 2. Что нужно исправить

Приоритеты: **P0** — заметно влияет на ежедневную работу; **P1** — надёжность и удобство; **P2** — защита в глубину и инженерные процессы; **P3** — качество кода и долгосрочная архитектура.

### P0

**F1. Путь `/v1` блокирует главный поток панели.**
Каждый запрос к API синхронно, в единственном потоке PowerShell, выполняет `Get-AiGatewayRuntime` (`src/Panel.Engine.ps1`): читает `gateway.json`, `config.json`, XML, опрашивает 2–3 службы и делает HTTP-probe движка с таймаутом 2 с. То же делает `/api/status` (`Get-AiDashboard`, при `gpu=1` ещё и `nvidia-smi`). Итог: лишняя задержка до первого токена, а зависший движок или медленный `nvidia-smi` на секунды останавливает всю панель и API.
Решение: кеш runtime-состояния выбранного движка (TTL 1–2 с), сброс при старте/завершении операций управления; сборка dashboard в фоновом ThreadJob с кешем, как уже сделано для телеметрии.

**F2. Второй параллельный запрос сразу получает 409.**
`InferenceStats.Begin` возвращает `null`, если идёт генерация. Клиенты (Jan, Open WebUI, агенты) часто отправляют параллельные запросы — например, генерацию заголовка чата — и получают ошибку.
Решение: FIFO-очередь ожидания в прокси (глубина 4, таймаут 60 с, настраивается в `gateway.json`), отмена ожидания при отключении клиента; операции управления по-прежнему имеют приоритет и блокируют выдачу новых слотов. Статус «в очереди» в журнале активности.

**F3. Упавший движок не поднимается сам.**
`Service.Host.exe` при аварийном завершении дочернего процесса останавливает службу с кодом ошибки, но recovery-действия SCM не настроены.
Решение: при установке задавать `sc failure` (перезапуск через 5 с / 30 с, далее без перезапуска, сброс счётчика через час) и `sc failureflag 1`; штатная остановка через панель/CLI сбоем не считается. В панели показывать «перезапущен после сбоя N раз» и последнюю ошибку из журнала.

### P1

**F4. Скачивание моделей без прогресса и докачки.**
GGUF качается `Invoke-WebRequest` с таймаутом 2 ч; Ollama pull — с `stream=false`. Обрыв на 30+ ГБ означает загрузку заново, а медленный канал упирается в таймаут. Прогресса и отмены в UI нет.
Решение: C#-загрузчик на `HttpClient` с `Range`-докачкой в `.part`, прогрессом (байты, скорость, ETA), отменой; Ollama pull со `stream=true` и разбором прогресса; таймаут по бездействию вместо общего.

**F5. Остатки `.download-*.part`.** При аварийном завершении панели файлы остаются в каталоге моделей. Решение: очистка при старте или переиспользование для докачки (вместе с F4).

**F6. Сессии теряются при перезапуске панели, в том числе после каждого обновления.**
Решение: хранить сессии в файле, защищённом DPAPI (LocalMachine), с хэшами идентификаторов вместо самих токенов; срок жизни прежний.

**F7. Статика без кеширования.** Каждый ответ `no-store`, шрифты (~220 КБ) читаются с диска и декодируются из base64 при каждом запросе. Решение: загрузка в память при старте, `ETag` и `Cache-Control: max-age` для шрифтов/SVG/CSS/JS; `no-store` оставить для `/api/*`.

**F8. Все ошибки возвращаются как `400` с текстом исключения.** Внутренние сбои должны давать `500` с общим сообщением (подробность — в журнал панели); `400` — только для ошибок валидации.

### P2 — защита в глубину

**S1. API без ключа через NAS.** Маршрут `/v1` не учитывает, пришёл ли запрос через доверенный proxy; при выключенном ключе API доступен любому устройству в WireGuard/LAN. Решение: для запросов от `trusted_proxy_addresses` ключ обязателен, либо в UI запрет выключения ключа при настроенном `public_origin` с явным предупреждением.

**S2. PBKDF2 в главном потоке.** Каждая попытка входа занимает ~0,1–0,3 с единственного потока. Решение: глобальный лимит попыток в секунду и/или проверка пароля вне главного цикла.

**S3. Неверная настройка `X-Forwarded-For`.** Если NAS начнёт дописывать цепочку, все клиенты попадут в один счётчик попыток с IP NAS, и шесть ошибок заблокируют вход всем. Решение: явно отклонять/журналировать заголовок с цепочкой; вести журнал входов (время, IP, результат).

**S4. TOTP (опционально).** Второй фактор для панели; при доступе только через WireGuard — низкий приоритет.

### P2 — инженерные процессы

**E1. Нет CI.** GitHub Actions на `windows-latest`: `test.ps1`, `update_test.ps1`, `install_flow_test.ps1`, `native_host_test.ps1`, `http_test.py`, `web_test.cjs`, проверка, что `dist/` собран из текущих исходников.

**E2. Версия `0.9.4` вписана вручную примерно в 6 файлов кода и несколько тестов.** Решение: один файл `VERSION`, чтение при старте/сборке, тесты сверяют с ним.

**E3. Собранный `dist/install-omnibox-ai.ps1` (426 КБ) коммитится в `main`.** Решение: теги и GitHub Releases, сборка в CI. Переход только с обратной совместимостью: установленные версии обновляются из `dist/...?ref=main`, поэтому путь сохраняется до перехода всех установок на новый механизм.

**E4. Работа напрямую в `main`.** Ветки и PR, чтобы CI проверял изменения до слияния.

### P3

**Q1. Плотный код.** Много операторов в одной строке через `;` в `Panel.Engine.ps1`, `Panel.Server.psm1`, `web/app.js`. Постепенное форматирование при изменении соответствующих участков.

**Q2. HTTP-хост на C#.** Прокси, статистика и служба уже на C#; однопоточный цикл PowerShell остаётся узким местом. Долгосрочно — перенос HTTP-хоста панели на ASP.NET Core/Kestrel, PowerShell остаётся для установщика и CLI. Решение принимается после этапов 1–3 по результатам замеров.

## 3. Дальнейшее развитие

По убыванию пользы для сценария «ноутбук через WireGuard → домашний ПК»:

1. **Автопереключение моделей по запросу** (как llama-swap). Клиент указывает модель, панель сама останавливает текущий движок и загружает нужную, запрос ждёт в очереди (опирается на F2). Список доступных моделей отдаётся в `/v1/models`. Политика: разрешённые модели, таймаут загрузки, запрет переключения во время генерации.
2. **Оценка «поместится ли модель в VRAM»** до скачивания и загрузки: по метаданным GGUF (слои, размер, квантизация), контексту и типу KV cache; рекомендация GPU layers.
3. **Пресеты запуска** («код 32k», «чат 128k на CPU») и переключение одним действием.
4. **Несколько API-ключей**: имя, отзыв, дата последнего использования, токены по ключу (Jan, Pi, телефон).
5. **Новые движки**: обычный llama.cpp, KoboldCpp, LM Studio; позже отдельные endpoints для эмбеддингов, Whisper (STT) и TTS.
6. **Проверка модели из панели**: короткий тестовый промпт и замер tok/s (prompt/generation) — бенчмарк после смены настроек.
7. **Пробуждение и уведомления**: Wake-on-LAN через NAS, если ПК спит; уведомления (Telegram) о падении движка и завершении скачивания.
8. **PWA** для телефона: установка на главный экран, адаптивные вкладки.

## 4. План реализации

Каждый этап — отдельная ветка, PR с прогоном CI, запись в `CHANGELOG.md`, сборка `dist/`, проверка на серверном ПК после обновления.

### Этап 0 — 0.9.5: страховочная сетка
- E1: workflow GitHub Actions со всеми наборами тестов.
- E2: файл `VERSION`, удаление жёстко прописанных версий.
- E4: работа через ветки и PR.

Готово, когда: CI зелёный на `main`, повышение версии меняет один файл.

### Этап 1 — 0.9.6: быстрый и устойчивый `/v1`
- F1: кеш runtime-состояния, фоновая сборка dashboard.
- F2: очередь запросов в прокси.
- F7: кеш статики; F8: коды ошибок.
- S1: обязательный ключ для запросов через NAS.

Готово, когда: два одновременных запроса из клиента выполняются последовательно без 409; зависший движок не блокирует `/api/status` и вход; накладные расходы панели до отправки upstream-запроса измерены и не превышают 20 мс в тёплом кеше.
Тесты: HTTP-тесты на очередь (порядок, таймаут, отмена при отключении клиента, приоритет stop/unload), на кеш и его сброс.

### Этап 2 — 0.9.7: надёжность служб и сессий
- F3: recovery-действия SCM, счётчик сбоев в панели.
- F6: сессии переживают перезапуск.
- S2, S3: лимит входа и журнал входов.

Готово, когда: аварийно завершённый `llama-server` поднимается сам не более двух раз подряд; после `Обновления` панель остаётся залогиненной.
Проверка на ПК: принудительное завершение процесса движка, обновление из панели.

### Этап 3 — 0.10.0: скачивание моделей
- F4, F5: загрузчик с докачкой, прогрессом и отменой; стриминговый Ollama pull.
- Отображение очереди/прогресса на вкладке «Модели».

Готово, когда: обрыв сети на середине загрузки GGUF продолжается с того же байта; отмена удаляет `.part`; прогресс виден для GGUF и Ollama.

### Этап 4 — 0.11.0: модели по запросу
- Развитие 1: автопереключение по полю `model`.
- Развитие 2: оценка VRAM.
- Развитие 3: пресеты.

Готово, когда: запрос с другой разрешённой моделью загружает её и получает ответ без действий в панели; модель, которая не помещается, помечена до загрузки.

### Этап 5 — 0.12.0: клиенты и наблюдаемость
- Развитие 4: несколько API-ключей и статистика по ключам.
- Развитие 6: тестовый промпт и tok/s.
- Развитие 7: уведомления; Wake-on-LAN — при наличии поддержки на NAS.

### Этап 6 — 1.0.0: архитектура и релизы
