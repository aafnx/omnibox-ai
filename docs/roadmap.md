# План развития OmniBox AI

Состояние на 2026-10-08, версия **0.20.3**. Документ фиксирует, что уже сделано, что нужно исправить (по приоритету) и куда развивать проект. В конце — поэтапный план реализации с критериями готовности и журнал выполненного по версиям.

План обновляется в каждом PR: выполненное отмечается в разделе 6 «Выполнено по версиям», новые задачи и найденные проблемы добавляются в разделы 2–4 (см. `AGENTS.md`).

Редакция 3: учтены ответы на открытые вопросы и два ревью плана (надёжность обновлений и сохранение настроек, нагрузка в простое, проверка движка вне главного потока, управляемый автоперезапуск с очисткой дерева процессов, семантика очереди и докачки, тесты сохранения входа, сохранение работы без API key, Wake-on-LAN через Home Assistant).

## Сценарий и исходные данные

- Серверный ПК с Windows дома: **RTX 5080 16 ГБ VRAM, 32 ГБ RAM**. Движки PrismML `llama-server` (Bonsai PQ2, MoE-модели вроде Ornith 1.5 35B-A3B) и **Ollama — оба остаются**; vLLM не используется (на Windows требует WSL2/Docker и держит все веса в VRAM). Панель и движки работают как службы ОС (Go-версия: `omnibox`, `omnibox-prismml`, `omnibox-ollama`).
- Клиенты API: **Jan, Pi, Open WebUI**, возможно появятся другие. Open WebUI и агенты отправляют параллельные служебные запросы (заголовки, теги, подсказки) — это важно для очереди.
- Доступ: LAN и **WireGuard**. NAS **Synology DS224+** выполняет reverse proxy: `https://llm.fnx.red/` → панель, `https://llm.fnx.red/v1` → OpenAI API, upstream `http://192.168.1.77:18090` у PowerShell-версии и `http://192.168.1.77:8800` у Go-версии.
- `llm.fnx.red` доступен только внутри WireGuard и LAN. Это **условие развёртывания**, а не свойство приложения: по исходникам проверить недоступность домена из интернета нельзя. Наличие `public_origin` или reverse proxy само по себе не означает публичный доступ.
- Wake-on-LAN отправляет **Home Assistant**. Панель работает на том же ПК и, пока он спит, недоступна, поэтому кнопка пробуждения и страница-заглушка размещаются в Home Assistant или на NAS, а не в панели.

### Принципы, которые план не нарушает

1. **Минимальная нагрузка в простое**: никаких фоновых таймеров опроса служб, GPU и моделей; всё вычисляется по запросу пользователя или клиента.
2. **Модель выбирается в панели**: запрос не может сам загрузить другую модель или запустить остановленный сервер. Автопереключение — только как отдельная опция, выключенная по умолчанию.
3. **Работа без API key разрешена**: переключатель ключа сохраняется.
4. **После команды «Остановить» сервер остаётся остановленным** при любых сценариях восстановления.
5. **Одна модель и одна генерация одновременно**.

## 1. Что уже реализовано

### Управление движками
- Два типа движков: PrismML `llama-server` и Ollama; имена служб, порты и пути задаются в `config.json`.
- Эксклюзивность: запуск одного движка останавливает остальные; один слот PrismML (`-np 1`), одна модель и один параллельный запрос Ollama.
- Запуск/остановка/перезапуск, «Остановить все серверы», ожидание готовности API (`/health`, `/api/version`).
- Настройки запуска через XML-профиль: контекст, время простоя, GPU layers, слои MoE в RAM (`--n-cpu-moe`), Flash Attention, все кванты KV cache llama-server, KV на GPU, потоки, mlock/mmap, batch/ubatch, размещение RAM/VRAM/гибрид; Thinking (`--reasoning`, уровень и лимит размышлений) и сэмплинг по умолчанию (temperature, top-k/p, min-p, штрафы, лимит токенов, seed). Обычный и продвинутый режим настроек.
- Управление движками: версии PrismML и Ollama с GitHub, обновление до последней, выбор версии, установка с нуля (служба, профиль, запись в `config.json`) и удаление с сохранением моделей; удаление моделей. Движок в панели называется по runtime — PrismML (служба исторически `bonsai`, в CLI работают оба имени).
- «Сохранить на следующий запуск» или «Применить сейчас»; автоматический откат XML при неудачном запуске, `ai restore`, история с SHA256 и флагом pending.
- Системный mutex `Global\omnibox-ai-control-v1` сериализует управление из CLI и панели (в Go-версии не нужен: управляет только служба).

### Собственный service runtime
- `Service.Host.exe` (C#, собирается встроенным `csc.exe`): регистрация в SCM, Job Object для дерева процессов, журналы с ротацией 3 × 4 МиБ, `runtime.json` (PID, offload слоёв на GPU).
- Миграция со старых `pwsh service.ps1` и WinSW-служб через проверенный `Win32_Service.Change`.

### Веб-панель
- Вкладки: обзор, модели, подключение, журналы, обновления; светлая/тёмная/системная тема (по умолчанию — системная), оформление по брендбуку OMNIBOX 1.0 (`docs/brand/`), логотип OMNIBOX AI, нижняя панель вкладок на телефоне, локальные шрифты Inter.
- Мониторинг CPU/RAM/GPU/VRAM/температур/вентиляторов только при открытой вкладке и работающем движке; без фонового опроса.
- Активность модели: текущий запрос, input/output/total токены, заполнение контекста, итоги по модельным сеансам. Журнал запросов хранится на диске и **восстанавливается после перезапуска панели**; по выбору владельца — с содержимым запросов и ответов (просмотр в панели).
- Место на диске: локальные диски (занято, всего, свободно, что на них хранится), объём моделей каждого движка, журналов, резервных копий, обновлений и движков; предупреждение о нехватке места на диске моделей; срок хранения журналов и порог предупреждения; очистка при запуске панели, установке и по кнопке.
- Каталог Hugging Face: поиск GGUF-репозиториев и файлов, скачивание GGUF с проверкой заголовка и SHA256; `ollama pull` по имени.
- Отсчёт до выгрузки по простою, фактическое размещение модели (RAM/VRAM/гибрид).

### OpenAI-совместимый API
- `/v1/models`, `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/responses` на порту панели (и опционально на отдельном порту).
- Асинхронный C#-прокси (`OpenAi.Proxy.cs`): SSE со сбросом буфера, лимит тела 8 МиБ, таймаут 30 мин, только loopback-upstream, без редиректов; различает статусы 401/404/409/413/415/429/502/503/504.
- API key (SHA256-хэш, сравнение за постоянное время) или работа без ключа; отдельный `upstream_api_key` для движка.
- Принимается только выбранная модель; контекст и размещение фиксируются панелью (`num_ctx`, `num_gpu`).
- Сбор usage из JSON/SSE, принудительный `include_usage` для стриминга.

### Безопасность панели
- Пароль PBKDF2-SHA256 (210 000 итераций), блокировка IP после 6 ошибок на 5 минут.
- Сессии входа 8 ч, cookie `HttpOnly; SameSite=Strict; Secure` (за proxy), CSRF-токен, проверка Origin и Host.
- Доверие `X-Forwarded-*` только от перечисленных IP NAS; CSP, `X-Frame-Options`, `nosniff`.
- Фиксированные маршруты, нет исполнения команд и чтения произвольных файлов через API.

### Установка и обновления
- Единый установщик `dist/install-omnibox-ai.ps1` со встроенным пакетом и SHA256, мастер настройки, ACL и Firewall; резервная копия заменяемых файлов в `backups/`.

- Транзакционная установка с замками, снимком и автоматическим откатом; проверка настроек по значениям; три последние резервные копии каждого вида.
- Обновление из веб-панели: вход gh по коду или разовый токен, DPAPI-хранение, временная служба-worker с копией runtime, общий mutex управления, снимок приложения и попытка восстановления при сбое, сохранение результата между перезапусками панели.

### CLI
- `ai start/stop/restart/context/restore/status/power/logs/endpoint/config/update/access/password reset/storage/engine/version/help`, сквозные команды Ollama. Сообщения короткие, сначала движок, затем модель.

## 2. Что нужно исправить

Приоритеты: **P0** — риск поломки установки или заметное влияние на ежедневную работу; **P1** — надёжность и удобство; **P2** — защита в глубину; **P3** — качество кода и долгосрочная архитектура.

### P0

**U1. Надёжность обновлений и установки.** Выполнено в 0.9.5 (замки установки и управления, транзакция с автоматическим откатом, проверка настроек по значениям); ниже — исходная постановка.
Подтверждено по коду (до 0.9.5):
- веб-worker (`scripts/update-worker.ps1`) берёт mutex `Global\omnibox-ai-control-v1`, а `ai update` и `install.ps1` — нет. CLI-обновление может идти одновременно с веб-обновлением или с управлением движками из панели;
- установщик делает резервную копию заменяемых файлов, но после начала копирования нет общего обработчика, который при любой последующей ошибке (миграция служб, ACL, Firewall, запуск панели) вернёт согласованный комплект; полное восстановление есть только в веб-worker.

Решение:
- единый замок установки, который берёт **сам установщик** независимо от способа запуска (CLI, веб-worker, ручной запуск). Предотвратить взаимоблокировку: worker не должен держать mutex, пока ждёт дочерний установщик, который пытается взять тот же mutex, — нужна явная передача владения или раздельные замки «установка» и «управление» с фиксированным порядком захвата;
- на время замены файлов запрещены операции управления движками и новые генерации (для панели — уже есть guard; для CLI — через тот же замок);
- транзакционная установка: журнал шагов, снимок файлов приложения, XML-профилей и команд служб (`PathName`, тип запуска) до изменений; при ошибке на любом шаге — автоматическое восстановление снимка и прежних команд служб, затем запуск панели в прежней версии;
- одинаковое поведение для CLI и веб-обновления; результат с причиной и статусом восстановления;
- проверка сохранения пользовательских данных **после успешного обновления и после отката**: hash пароля панели (`panel.json`), hash API key и настройки API (`gateway.json`), адреса панели, `public_origin` и `trusted_proxy_addresses` NAS, `config.json` (движки, пути, выбранная модель Ollama), XML-профили движков с настройками моделей, история отката `.ai-previous`/`.ai-state.json`, сохранённый доступ gh для веб-обновлений. Способ сравнения зависит от типа данных:
  - **пользовательские настройки сравниваются по значениям**, а не по hash файла: из `panel.json`, `gateway.json`, `config.json` и XML-профилей до установки извлекается нормализованный набор значений (hash/salt/итерации пароля, hash ключа и `require_key`, порты, адреса, Base URL, выбранный движок, NAS-настройки, пути и выбранные модели, токены аргументов движка, переменные окружения). Форматирование, порядок полей и предусмотренная миграция структуры не считаются изменением. Для миграций задаётся явное правило «старое значение → ожидаемое новое», и после установки значения сверяются с ожидаемыми;
  - **побайтово (hash)** проверяются только файлы, которые установщик не должен изменять: история отката (`.ai-previous`, `.ai-state.json` — она сама содержит SHA256 XML), файл сохранённого доступа gh. Проверка выполняется до запуска панели, чтобы её собственные записи не давали ложных расхождений;
  - любое расхождение — ошибка установки и откат.

**F1. Путь `/v1` блокирует главный поток панели.** Выполнено в 0.17.0: проверка ключа до проверок движка; проверки runtime и `/api/status` в ThreadJob по запросу; общий кеш runtime на секунду с одной проверкой при промахе, сбросом при управлении и защитой от устаревшего состояния. Ниже — исходная постановка.
Каждый запрос к API синхронно, в единственном потоке PowerShell, выполняет `Get-AiGatewayRuntime` (`src/Panel.Engine.ps1`): читает `gateway.json`, `config.json`, XML, опрашивает 2–3 службы и делает HTTP-probe движка с таймаутом 2 с. Даже запрос с неверным ключом сначала проходит все эти проверки, потому что ключ сверяется уже в C#-прокси. `/api/status` (`Get-AiDashboard`, при `gpu=1` ещё и `nvidia-smi`) также выполняется в главном потоке.
Решение:
- проверять API key **до** любых обращений к службам и движку;
- проверка состояния движка (службы, профиль, probe API) выполняется **вне главного HTTP-потока**, в том числе первая проверка при пустом или просроченном кеше: главный поток только передаёт контекст запроса асинхронной задаче. Предпочтительно перенести проверку в C# (`ServiceController`, async `HttpClient`) рядом с прокси; одновременные запросы при промахе кеша ждут одну общую проверку, а не запускают несколько;
- кешировать runtime-состояние выбранного движка **только по запросу**: значение вычисляется при поступлении запроса и переиспользуется короткое время (1–2 с); без фонового таймера; сброс при старте и завершении операций управления. Кеш устраняет повторные задержки, а вынос проверки из главного потока — блокировку панели;
- `/api/status` собирать в ThreadJob, запускаемом запросом браузера (как телеметрия), без собственного периодического опроса.

**F2. Второй параллельный запрос сразу получает 409.**
Сейчас 409 — сознательная защита от параллельной генерации, но для Open WebUI, Jan и Pi это ошибки на служебных запросах. Решение — ограниченная FIFO-очередь в прокси при сохранении одной генерации одновременно.
Семантика:
- запрос в очереди привязан к движку, модели и «поколению» состояния сервера на момент постановки;
- остановка, выгрузка, смена модели или настроек, обновление приложения увеличивают поколение: все ожидающие запросы немедленно получают 503/409 с понятным сообщением и **никогда** не выполняются на другой модели;
- очередь не запускает остановленный сервер и не загружает модель;
- отключение клиента удаляет запрос из очереди;
- глубина и таймаут ожидания настраиваются в `gateway.json` (предложение по умолчанию: 4 запроса, 60 с); глубина 0 — прежнее поведение с немедленным 409;
- ожидание отображается в активности панели как «в очереди».

### P1

**F4. Скачивание моделей без прогресса, отмены и докачки.** Выполнено в Go-версии (`internal/catalog`, операции `download`/`pull`): прогресс и скорость в списке операций, отмена (`{"action":"cancel","id":…}`), таймаут по бездействию, докачка по ссылке с ревизией-коммитом или с тем же ETag (`If-Range`), проверка `Content-Range`, размера, заголовка GGUF и SHA256, проверка свободного места; Ollama pull со `stream=true`. Ниже — исходная постановка.
GGUF качается `Invoke-WebRequest` с общим таймаутом 2 ч; Ollama pull — с `stream=false`. Обрыв на 30+ ГБ означает загрузку заново.
Решение:
- C#-загрузчик на `HttpClient` с прогрессом (байты, скорость, ETA) и отменой; таймаут по бездействию вместо общего;
- докачка в `.part` через `Range` только при неизменном файле на сервере: сохранять `ETag`/размер/ревизию HF и отправлять `If-Range`; ответ `206` с корректным `Content-Range` — продолжать, `200` — начинать заново, `416` и несоответствия — сбрасывать `.part`;
- итоговая проверка: размер равен ожидаемому, заголовок `GGUF`, SHA256 из метаданных HF, если доступен;
- Ollama pull со `stream=true` и разбором прогресса.

**F5. Остатки `.download-*.part`.** Выполнено в Go-версии: рядом с `.part` хранятся метаданные докачки (`.json`: ссылка, ETag, размер), отмена удаляет оба файла, а не продолженные неделю удаляет очистка хранения.

**F7. Статика без кеширования.** Выполнено в 0.19.0: ETag, `no-cache` для страницы, скрипта и стилей, неделя для шрифтов и SVG. Ниже — исходная постановка. Каждый ответ `no-store`, шрифты (~220 КБ) читаются с диска и декодируются из base64 при каждом запросе.
Решение: файлы загружаются в память при старте; шрифты и SVG — `Cache-Control: max-age` с версией в URL; `app.js` и `style.css` — URL с версией (`?v=<VERSION>`) или `ETag` + `no-cache`, чтобы **после обновления клиент гарантированно получил новый JS/CSS**; `/api/*` остаётся `no-store`.

**F8. Общий обработчик панели возвращает любые ошибки как `400` с текстом исключения.** Выполнено в 0.19.0: 400 для проверок, 500 и `logs/panel.log` для системных сбоев. Ниже — исходная постановка. Валидация — `400`, внутренние сбои — `500` с общим сообщением, подробности — в журнал панели. C#-прокси `/v1` уже различает статусы и не меняется.

**F3. Управляемое восстановление движка после сбоя.** Выполнено в 0.19.0 (Go-версия): `auto_restart` у движка, выключен по умолчанию; перезапуск внутри хоста службы через 5 с, не больше 2 за 10 минут; остановка службы отменяет и ожидающий перезапуск; при сообщениях о нехватке памяти попытки прекращаются; после выхода движка дерево процессов завершается до нового запуска. Желаемое состояние отдельно не хранится: остановка — это остановка службы, и перезапуск идёт только внутри работающей службы. Ниже — исходная постановка.
`Service.Host.exe` при аварийном завершении дочернего процесса останавливает службу; восстановления нет. Простое `sc failure` недостаточно: Windows может выполнить уже запланированный recovery-перезапуск даже после последующей ручной остановки.
Решение:
- отдельная настройка автоперезапуска для каждого движка, **выключена по умолчанию**;
- учёт желаемого состояния (`desired: running/stopped`), который панель и CLI записывают до остановки; восстановление выполняется только при `desired = running`;
- перезапуск дочернего процесса внутри `Service.Host.exe` с задержкой (без SCM recovery actions): штатная остановка службы устанавливает событие Stop, и перезапуск становится невозможен;
- перед повторным запуском завершается **всё дерево** предыдущего движка, включая Ollama runners. Сейчас Job Object с `KILL_ON_JOB_CLOSE` охватывает сам host и очищает дерево только при завершении host; если host продолжает работать, потомки упавшего процесса могут остаться и удерживать VRAM и порт. Решение: отдельный Job Object на каждый запуск движка, `TerminateJobObject` и ожидание завершения всех процессов задания перед новым стартом; закрытие host по-прежнему завершает всё;
- ограничение попыток (например, 2 за 10 минут) и прекращение попыток при повторных ошибках нехватки памяти (по журналу движка: CUDA/alloc/out of memory);
- в панели: счётчик перезапусков, последняя ошибка, кнопка сброса.
Обязательные тесты: «сбой → остановка пользователем → движок не запускается снова»; «сбой движка с дочерними процессами → перезапуск → процессов прежнего запуска не осталось».

**F6. Сессии входа в панель теряются при перезапуске панели** — выполнено в 0.17.1: DPAPI LocalMachine, хэши идентификаторов, абсолютный срок восемь часов, отзыв при выходе и смене пароля. Ниже — исходная постановка: в том числе после каждого обновления. (Журнал запросов и итоги модельных сеансов уже восстанавливаются.) Решение: хранить сессии входа в файле, защищённом DPAPI (LocalMachine), с хэшами идентификаторов вместо самих токенов; срок жизни прежний.
Обязательные тесты: смена или сброс пароля аннулирует все сохранённые сессии; выход удаляет сессию с диска; перезапуск панели не продлевает восьмичасовой срок (хранится абсолютное время истечения); повреждённый или нерасшифровываемый файл сессий приводит к повторному входу, а не к ошибке панели.

### P2 — защита в глубину

С учётом доступа только из LAN/WireGuard это не срочные меры; они ограничивают ущерб от скомпрометированного устройства внутри сети.

**S1. Предупреждение о работе без ключа.** Выполнено в 0.19.0. Переключатель API key сохраняется, работа без ключа остаётся разрешённой. В панели — заметное предупреждение, если ключ выключен, и подсказка, что это допустимо только при закрытой сети.

**S2. PBKDF2 в главном потоке.** Выполнено в Go-версии: проверка пароля вне блокировки, в 0.19.0 — не больше двух проверок одновременно, остальные попытки получают 429. Каждая попытка входа занимает ~0,1–0,3 с единственного потока. Решение: глобальный лимит попыток в секунду и/или проверка пароля вне главного цикла.

**S3. Неверная настройка `X-Forwarded-For`.** Выполнено в 0.19.0: от NAS берётся последний адрес цепочки (его видел сам NAS), поэтому поддельное начало цепочки не попадает в чужой счётчик, а клиенты не сливаются в один; журнал входов — в `logs/panel.log` (время, IP, через NAS или напрямую, результат, блокировка). Если NAS начнёт дописывать цепочку, все клиенты попадут в один счётчик попыток с IP NAS, и шесть ошибок заблокируют вход всем. Решение: явно отклонять/журналировать заголовок с цепочкой; журнал входов (время, IP, результат).

**S4. TOTP (опционально).** Низкий приоритет.

## 3. Дальнейшее развитие

Для сценария «ноутбук/телефон через WireGuard → домашний ПК с RTX 5080 16 ГБ»:

1. **Пресеты запуска** (выполнено в 0.19.0) («код 32k», «чат 128k», «CPU») — сохранённые наборы настроек, применяемые одним действием через существующий механизм отката.
2. **Оценка размещения в 16 ГБ VRAM / 32 ГБ RAM** (выполнено в 0.19.0 для PrismML) до скачивания и загрузки: по метаданным GGUF (слои, размер, квантизация), контексту и типу KV cache; рекомендация GPU layers и предупреждение о переполнении.
3. **Тест модели из панели** (выполнено в 0.19.0): короткий фиксированный промпт и показатели prompt/generation tok/s, время до первого токена — сравнение после смены настроек и пресетов.
4. **Несколько API-ключей** (выполнено в 0.19.0): имя, отзыв, последнее использование, токены по ключу (Jan, Pi, Open WebUI). Режим без ключа сохраняется.
5. **Сон и пробуждение** (выполнено в 0.19.0: кнопка в панели, MAC в «Подключении», `docs/sleep.md`): в панели — команда «Перевести ПК в сон» (с отказом во время генерации, скачивания и обновления); пробуждение — скрипт `wake_on_lan` и кнопка в **Home Assistant**, страница-заглушка «ПК спит» — в Home Assistant или на NAS. Панель на спящем ПК недоступна и разбудить его не может, поэтому в репозитории — только инструкция и пример конфигурации HA.
6. **Уведомления — отложены.** Возможная схема на будущее: панель в момент события отправляет webhook в Home Assistant (падение движка, завершение скачивания, результат обновления, блокировка входа), доставку настраивает HA; без фонового опроса.
7. **Автопереключение моделей по запросу** — опция, **выключенная по умолчанию**: клиент указывает модель из разрешённого списка, панель загружает её с учётом очереди (F2) и правил поколений. Меняет принцип «модель выбирается в панели», поэтому только явное включение.
8. **Новые движки**: обычный llama.cpp, KoboldCpp; отдельные endpoints для эмбеддингов, Whisper, TTS — по необходимости. Основа есть с 0.15.0: менеджер движков ставит и обновляет runtime из выпусков GitHub.
10. **Speculative decoding** (MTP, DFlash-черновик) для PrismML — ускорение генерации; у Ornith есть DFlash-версия, требует проверки на ПК.
11. **Просмотр содержимого запросов** (выполнено в 0.19.0: поиск и экспорт сеанса) с поиском и экспортом сеанса (сейчас — открытие отдельного запроса).
9. **PWA** для телефона — выполнено в 0.19.0.
12. **Удобство панели (запрос владельца, 0.20.0)**:
    - рекомендуемые настройки по умолчанию — пресет «Базовый» под модель и VRAM и предупреждение о переполнении VRAM (выполнено в 0.20.0);

    - компактный обзор (карточки ресурсов) и форма настроек модели по брендбуку (выполнено в 0.20.0);
    - каталог установленных моделей: все модели движка с размером, квантизацией и ссылкой на Hugging Face, выбор и удаление любой незагруженной модели (выполнено в 0.20.0);
    - имя модели в API формируется из названия модели автоматически (выполнено в 0.20.0);
    - возможности модели значками, как на openrouter.ai: рассуждения, зрение, инструменты, контекст (выполнено в 0.20.0);

## 4. План реализации

Каждый этап — отдельная ветка и PR с прогоном CI, запись в `CHANGELOG.md` для пользовательских версий, обновление этого плана, проверка на серверном ПК после установки. Номера версий этапов назначаются при выпуске: этапы 0.9.6–0.15.0 ушли на задачи владельца из раздела 6, поэтому оставшиеся этапы ниже не привязаны к номерам.

### Этап G: переход на Go — выпущен в 0.18.0, остаются E и доработки

Решение владельца после 0.17.1: программа переписывается на Go — один бинарник для Windows и Linux, состояние в памяти одного процесса, движки остаются отдельными службами, CLI работает через службу. Без наследия: один `config.json` нового формата, профили движков в JSON вместо XML, новые имена служб и каталоги; чистая установка без переноса данных, мастер установки проходится одними Enter. Проект: [`architecture-go.md`](architecture-go.md), согласован (раздел 11 — решения владельца: движки отдельными службами, CLI через службу, подпись бинарника, температура CPU через LibreHardwareMonitor, нумерация продолжается по порядку, установка и обновление одной командой). F2, F3, F4/F5, F7, F8, S1–S3 и развитие из раздела 3 делаются в Go-версии. По решению владельца PowerShell-код, его тесты, `dist/`, `releases.json` и документация PowerShell-версии удалены из `main` досрочно, после части B; последняя PowerShell-версия — ветка `powershell-0.17.1`, исправления для неё больше не выпускаются.

- A: каркас, настройки, вход и статус. Начат: модуль Go и бинарник `omnibox serve`; новый единый `config.json` (панель, API, хранение, движки `prismml`/`ollama` со структурированными настройками и откатом `previous`/`pending` в той же записи) с проверками и тестами; правила настроек движков перенесены из PowerShell; чтение и атомарная запись файлов для Windows и Linux; вход (PBKDF2), сессии, CSRF, Origin, reverse proxy, статика; Go-тесты и сборка Windows/Linux в CI. Влит в `main` (PR #20). Дальше: службы ОС (SCM, systemd), сборка командной строки движков, список моделей и проверки API — сделаны; затем `/api/status`, телеметрия, хост движков и управление.
- B: контроллер с откатом и поколениями, хост движков, `/v1` с очередью (F2). Начат: контроллер управления (`internal/control`) — запуск с остановкой другого движка и ожиданием API, применение и откат настроек, сохранение для следующего запуска, восстановление, загрузка и выгрузка моделей Ollama, скачивание; `POST /api/actions` как фоновые операции и их список в `/api/status`; режим `omnibox engine <движок>` — хост службы с Job Object (Windows) или группой процессов (Linux), журналами с ротацией и `runtime.json`. Затем `/v1` (`internal/gateway`): проверка ключа до служб, запросы идут на запущенный движок под настоящим именем модели, очередь F2 с поколениями, учёт токенов из JSON и SSE, `X-Accel-Buffering: no`, журналы `requests.jsonl` и необязательный `content.jsonl` с ротацией, `/api/activity` и `/api/request-content`. Дальше: этап C — хранение, менеджер движков, каталог, настройки API в панели.
- C: менеджер движков, хранение, каталог и докачка (F4/F5), обновление, расширенный мониторинг (температуры, NVML). Начат: хранение (`internal/storage`) — объём журналов движков и запросов, содержимого запросов, движков и моделей каждого движка, диски с ролями и предупреждением о нехватке места (Windows — фиксированные диски, Linux — локальные файловые системы), очистка по сроку хранения и незавершённых установок движков при запуске службы и по кнопке, `GET`/`POST /api/storage`; выключение журнала содержимого удаляет сохранённый текст. Затем менеджер движков (`internal/enginemgr`, операции в `internal/control`): список выпусков PrismML и Ollama с GitHub по запросу владельца (`GET /api/engine-releases?engine=`), установка версии с проверкой размера, SHA256, путей архива (zip и tar.gz) и пробного запуска `--version`, установка движка с нуля (служба с ручным запуском и запись в `config.json`), смена версии (работающий движок перезапускается после завершения текущей генерации и откатывается при сбое, остановленный проверяет версию при следующем запуске), удаление движка с сохранением моделей, удаление моделей, кроме выбранной и нужной для отката; `GET /api/engines`. Сборки для Linux (`ubuntu-x64`, `ollama-linux-amd64.tgz`) описаны, проверка на Linux — этап E. Затем каталог и скачивание (`internal/catalog`): поиск GGUF на Hugging Face и список файлов репозитория со ссылками на текущий коммит (`GET /api/catalog?q=` / `?repo=`), скачивание GGUF с прогрессом, отменой и докачкой (F4, F5), потоковый Ollama pull.
- D: установка и обновление одной командой (`install.ps1` во встроенном Windows PowerShell, `install.sh` для Linux); CLI; перевод `web/app.js` на ответы Go-сервера; пользовательская документация Go-версии (установка, панель, API, reverse proxy) вместо удалённой. PowerShell-код уже удалён. Начата: настройки API в панели (`GET`/`POST /api/gateway`: включение, адрес для клиентов, режим ключа, глубина и ожидание очереди; новый ключ показывается один раз и сразу отзывает прежний, хранится только SHA256) и смена пароля панели (`POST /api/password` с проверкой текущего пароля и лимитом попыток; остальные сессии завершаются). Затем установщик `omnibox install` (`internal/install`): программа в `bin/<версия>` каталога программы (`C:\Program Files\OmniBox AI`, `/opt/omnibox`), данные в `C:\ProgramData\OmniBox AI` или `/var/lib/omnibox`; мастер с ответами по умолчанию (порт 8800, адреса ПК, адрес API, NAS — нет, движки — да, каталог моделей) и `--yes`; пароль и API key генерируются и показываются один раз; службы `omnibox` (автозапуск) и движков (вручную), правило Windows Firewall для локальной подсети; откат при сбое на любом шаге; движки скачиваются после установки, их сбой не отменяет её. Повторный запуск — обновление: настройки не меняются, службы переключаются на новую версию, при неответе панели возвращается прежняя, хранятся текущая и предыдущая версии. Журнал установки на диске (восстановление после прерванной установки) пока не перенесён. Затем установка одной командой: `install.ps1` (встроенный Windows PowerShell 5.1, UTF-8 с BOM) и `install.sh` скачивают выпуск через `gh` или с одноразовым токеном в памяти, сверяют SHA256 и запускают `omnibox install`; workflow `release.yml` собирает архивы для Windows и Linux, `SHA256SUMS` и публикует их с примечаниями из `CHANGELOG.md`; консоль Windows переключается на UTF-8, чтобы русский текст установщика читался. Подпись бинарника — шаг-заглушка до выбора сертификата. Затем интерфейс переведён на ответы Go-сервера: тип движка `prismml`, каталог и список версий движков без опроса задач, установка и обновление движков по имени, прогресс скачивания (объём, скорость, сколько осталось) и кнопка отмены, число запросов в очереди в активности, настройки очереди API вместо выбора движка (`/v1` обслуживает запущенный движок), смена пароля панели; вкладка «Обновления» показывает версию и команду обновления. Обновление кнопкой из панели и `ai update` (временная служба-установщик) перенесены на потом: пока обновление — та же команда установки. Затем команда `ai` (`internal/cli`, `internal/local`): клиент службы через unix-сокет `run/omnibox.sock` в каталоге данных, доступный только администраторам (на Windows каталог данных закрыт ACL «SYSTEM и Администраторы», на Linux — права root): `ai status`, `start`, `stop` (без имени — все), `restart`, `logs`, `password reset` (новый пароль показывается один раз, все входы завершаются), `key new`, `update` (подсказка с командой обновления), `version`. Установщик кладёт `ai.cmd` в каталог программы и добавляет его в PATH (Linux — `/usr/local/bin/ai`); при обновлении команда переключается на новую версию и возвращается при откате.
- E: Linux (systemd), проверка под WSL2.
- После 0.18.0: подпись бинарника после выбора сертификата.

## 5. Решённые вопросы

- Клиенты: Jan, Pi, Open WebUI; возможны другие.
- Оборудование: RTX 5080 16 ГБ VRAM, 32 ГБ RAM.
- Ollama остаётся вместе с PrismML.
- `llm.fnx.red` доступен только из LAN и WireGuard (условие развёртывания).
- Wake-on-LAN — через Home Assistant.
- Уведомления — отложены.
- Движок для MoE-моделей — PrismML `llama-server` с `--n-cpu-moe`, не vLLM и не Ollama (Ollama делит модель только целыми слоями).
- Значения сэмплинга и Thinking в панели — значения по умолчанию; параметры клиента в запросе важнее.
- Содержимое запросов пишется только при явном выборе владельца; при выключении удаляется.
- При удалении движка модели остаются; удаление моделей — отдельной кнопкой.
- Язык новой версии — Go (сравнивались .NET, Go, Python, Node.js); WSL2 как основной способ запуска на Windows отложен: переписывание нужно в любом случае, а нативная версия не теряет память и скорость на виртуальной машине. Linux-сборка — этап G-E.
- Правило зависимостей смягчено: Go-модули с открытыми лицензиями; Python и Node на ПК — только для необязательных возможностей.
- Go-версия: панель и API на порту 8800, движки на 8801/8802 (loopback). Клиенты используют один Base URL `https://llm.fnx.red/v1` независимо от движка и настоящие имена моделей; правило NAS упрощено (см. `architecture-go.md`, раздел 2.3).

F3: флажок «Перезапускать движок после сбоя» (`auto_restart`, по умолчанию выключен) — хост службы движка запускает упавший движок снова через 5 с, не больше 2 раз за 10 минут, не при нехватке памяти; остановка службы отменяет ожидающий перезапуск; перед новым запуском завершается всё дерево прежнего (Job Object или группа процессов); в панели и `ai status` — число автоперезапусков, последний сбой и причина прекращения попыток. `ai update [версия]` (`internal/selfupdate`): выпуск из приватного репозитория по token из `GH_TOKEN`, `gh auth token` или скрытого ввода; token только для GitHub API, файл — по подписанной ссылке без него; сверка с `SHA256SUMS`, распаковка и запуск `install --yes` нового выпуска; без версии и при уже последней — ничего не делает; вкладка «Обновления» предлагает `ai update` первым. `ai uninstall`: службы, правило Firewall, команда `ai` и PATH, каталог программы (на Windows — после выхода процесса); данные и модели — отдельными вопросами, по умолчанию остаются. Журнал установки: откат каждого шага — данные (`install-journal.json` в каталоге программы), записываются до шага; тот же откат выполняется при ошибке и, после обрыва (питание, закрытое окно), при следующем запуске установщика — новая установка убирается полностью, обновление возвращает прежнюю версию и перезапускает панель; повреждённый журнал останавливает установщик с понятной ошибкой. Обновление кнопкой из панели: вкладка «Обновления» принимает GitHub token (только для этого скачивания, в памяти) и версию; операция `self-update` скачивает и проверяет выпуск в `updates/<версия>`, регистрирует временную службу `omnibox-update` (`omnibox update-service`), которая запускает установщик новой версии (обновление с откатом, вывод в `logs/update.log`) и записывает результат в `run/update-result.json`; панель после перезапуска показывает результат, удаляет остановленную временную службу и скачанные файлы. Пресеты запуска (развитие 1): встроенные «Код 32k», «Чат 128k», «CPU» и до 20 своих на движок (`engines.<движок>.presets`), сохраняются из текущих настроек без модели; применение — как форма настроек: работающий движок перезапускается с откатом, остановленный получает настройки к следующему запуску. Тест модели (развитие 3): кнопка «Тест модели» отправляет фиксированный короткий запрос через очередь `/v1` (как клиент, без ключа: запрос рождается внутри службы) и показывает время до первого токена, скорость чтения запроса и генерации (у PrismML — из `timings` llama-server) в списке операций; запрос попадает в журнал как обычный. Несколько API-ключей (развитие 4): `api.keys` — имя, SHA256 и дата, до 20; ключ 0.18 (`key_hash`) становится ключом «Основной» при загрузке; все ключи сравниваются за постоянное время; запрос помнит короткий id ключа, по журналу считаются запросы, токены и последний запрос каждого ключа; панель создаёт и отзывает ключи по одному (последний требуемый отозвать нельзя), `ai key new` заменяет все одним. Сон (развитие 5): операция `sleep` — через 3 с `SetSuspendState` (Windows) или `systemctl suspend` (Linux); отказ во время генерации (через Gate) и любой другой операции (скачивание, установка движка, обновление); MAC-адреса адаптеров в `/api/status` и во вкладке «Подключение»; `docs/sleep.md` — Wake-on-LAN в Windows и пример Home Assistant. Оценка размещения (развитие 2, `internal/gguf`): заголовок GGUF (архитектура, слои, головы KV, длины ключей и значений, обученный контекст, эксперты) без чтения весов, с ограничениями на размер полей; KV-кеш = слои × контекст × головы KV × (длина ключа × тип K + длина значения × тип V); VRAM из nvidia-smi (иначе 16 ГБ), RAM системы; рекомендация слоёв на GPU и кнопка подставить их; `GET /api/estimate` читает только GGUF из каталога моделей. Содержимое запросов (развитие 11): поиск по тексту запросов, ответов и рассуждений в `content.jsonl` (по действию владельца, от 2 символов, до 50 совпадений, новые сверху) и экспорт сеанса файлом JSONL (`GET /api/request-content?q=` / `?session=…&export=1`). PWA (развитие 9): манифест, иконки из знака бренда (`scripts/render-icons.py`), service worker без кеша — на телефоне не остаются данные панели, а при недоступном ПК показывается подсказка вместо ошибки; регистрация только в защищённом контексте (HTTPS через NAS). По просьбе владельца — полный запуск и остановка и автозапуск: `ai on [движок]` (служба панели, ожидание готовности, затем модель), `ai off` (движки, затем панель), `ai autostart on|off` (тип запуска службы `omnibox`, `Services.SetAutomatic`: SCM или systemd enable/disable), `ai autostart model` и в панели «Запуск и выключение» (автозапуск, модель при старте, «Выключить OmniBox полностью» — отказ при работающей операции, генерация прерывается после подтверждения). Решение владельца: модель при старте (`panel.start_engine`, по умолчанию пусто) запускается один раз за загрузку ПК — отметка времени загрузки в `run/boot.json`; перезапуск службы в той же загрузке (обновление, сбой) модель не запускает, так что принцип 4 соблюдается. В README перечислены возможности 0.19.0.
