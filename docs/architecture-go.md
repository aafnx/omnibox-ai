# Архитектура OmniBox AI на Go

Статус: **согласован владельцем** (решения — раздел 11). Документ описывает новую версию OmniBox AI, которая заменит PowerShell-реализацию. Текущая архитектура — в [architecture.md](architecture.md); она действует, пока Go-версия не заменит её полностью.

## 1. Зачем переписывать

За версии 0.16–0.17 большинство дефектов пришлось на три группы:

| Группа | Примеры | Причина |
|---|---|---|
| Файлы на Windows | `Replace`/`Move` при открытом читателе, «пропадающий» путь, `Access denied` | Каждый запрос статуса в отдельном PowerShell-потоке заново читает `config.json` и XML с диска, пока другой поток их перезаписывает |
| Ловушки PowerShell | StrictMode, «разворачивание» массивов, вложенный `Import-Module -Force`, `LASTEXITCODE` в новом потоке | Сервер написан на скриптовом языке |
| Гонки управления | защита генерации, приём запросов во время обновления | Логика распределена между PowerShell-потоками, C#-прокси и системным mutex |

Первые две группы устраняются архитектурой: один процесс держит состояние в памяти, файлы пишет одно место, код компилируется со строгими типами. Третья группа остаётся задачей проектирования, но решается проще: обычные блокировки и каналы в одном процессе вместо флагов между runspace, C# и CLI.

Выбор языка (Go, .NET, Python, Node.js) обсуждён с владельцем; выбран **Go**: один исполняемый файл без среды выполнения, наименьшая память в простое, кросс-компиляция под Linux одной командой, разделение кода по ОС проверяется компилятором.

## 2. Без наследия

Решение владельца: Go-версия — новая программа, без исторических форматов и обходных путей. Совместимость сохраняется только там, где её видят внешние клиенты.

**Сохраняется:**
- **Принципы** из `AGENTS.md`: нет фонового опроса; модель выбирается в панели; работа без API key; «Остановить» — значит остановлен; одна модель и одна генерация; обновление не теряет данные и откатывается при сбое.
- **`/v1` для клиентов** — OpenAI-совместимый API на порту панели (18090), тот же ключ. Jan, Pi, Open WebUI и NAS не замечают перехода.
- **Интерфейс** `web/` — встраивается в бинарник; его можно менять вместе с API панели.

**Убирается:**
- XML-профили, `.ai-previous`/`.ai-state.json`, WinSW и `pwsh`-службы, их миграции;
- четыре файла настроек (`config.json`, `panel.json`, `gateway.json`, `storage.json`) — вместо них один `config.json` нового формата;
- историческое имя службы `bonsai` и псевдонимы CLI: движки называются `prismml` и `ollama`, службы — `omnibox`, `omnibox-prismml`, `omnibox-ollama`;
- отдельный порт API: `/v1` только на порту панели;
- `dist/` в `main`, `releases.json`, `gh` в продукте: выпуски — GitHub Releases;
- системный mutex управления: управляет только служба, CLI работает через неё.

### 2.1. Настройки

Один файл `config.json` в каталоге данных; пишет его только служба, атомарно.

```json
{
  "schema_version": 1,
  "panel": {
    "port": 18090,
    "hosts": ["192.168.1.77", "omnibox"],
    "public_origin": "https://llm.fnx.red",
    "trusted_proxies": ["192.168.1.10"],
    "password": { "salt": "…", "hash": "…", "iterations": 210000 }
  },
  "api": { "enabled": true, "public_url": "https://llm.fnx.red/v1", "require_key": true, "key_hash": "…", "engine": "prismml" },
  "storage": { "log_retention_days": 30, "log_warn_mb": 200, "request_log": "metadata" },
  "engines": {
    "prismml": {
      "port": 18080,
      "executable": "…\\engines\\prismml\\b6xxx\\llama-server.exe",
      "models_directory": "D:\\models",
      "settings": { "model": "…\\ornith.gguf", "alias": "ornith", "context": "32768", "gpu_layers": "999", "n_cpu_moe": "24" },
      "extra_arguments": ["--jinja"],
      "previous": { "…": "последняя рабочая конфигурация" },
      "pending": false
    },
    "ollama": { "port": 11434, "executable": "…", "settings": { "context": "32768", "keep_alive": "30m" }, "model": "qwen3:8b" }
  }
}
```

- Командная строка движка собирается из `settings` при запуске; правки текста аргументов нет. Неизвестные панели флаги хранятся в `extra_arguments`.
- Откат — в той же записи движка: `previous` (последняя рабочая конфигурация) и `pending` (изменение ещё не запускалось). Сбой запуска возвращает `previous`.
- Секреты — отдельно в `secrets/` (сессии входа, доступ к GitHub), под DPAPI на Windows и правами 0600 на Linux.

### 2.2. Раскладка и установка

| | Windows | Linux |
|---|---|---|
| Программа | `C:\Program Files\OmniBox AI\` (`omnibox.exe`, версии рядом для отката) | `/opt/omnibox/` |
| Данные | `C:\ProgramData\OmniBox AI\` (`config.json`, `secrets\`, `logs\`, `engines\`, `models\`) | `/var/lib/omnibox/`, журналы `/var/log/omnibox/` |

Модели по умолчанию в `models\`, каталог настраивается при установке и в панели (например, указать каталог с уже скачанными GGUF).

**Чистая установка** — решение владельца: данные PowerShell-версии не переносятся. Если установщик находит старые службы (`omnibox-ai`, `bonsai`, `ollama`), он предлагает их удалить (по умолчанию — да), потому что они занимают те же порты; их файлы остаются на диске.

**Мастер установки** задаёт вопросы с готовыми ответами по умолчанию, и его можно пройти, просто нажимая Enter:

| Вопрос | По умолчанию |
|---|---|
| Порт панели | 18090 |
| Адреса панели | найденные IPv4 этого ПК, имя компьютера, `localhost` |
| Пароль панели | сгенерировать и показать один раз |
| OpenAI API и ключ | включить, ключ сгенерировать и показать один раз |
| Адрес API для клиентов | `http://<IPv4>:18090/v1` |
| Reverse proxy (NAS) | нет |
| Движки | установить PrismML и Ollama последних версий |
| Каталог моделей | `models\` в каталоге данных |
| Удалить старые службы PowerShell-версии | да, если найдены |

Неинтерактивная установка (`--yes`) принимает все ответы по умолчанию.

## 3. Общая схема

```
omnibox.exe (один бинарник, разные режимы)
├── service   — служба omnibox-ai: панель, API, /v1, управление, мониторинг
├── engine    — хост одного движка (служба Windows / unit systemd), заменяет Service.Host.exe
├── ai ...    — CLI: клиент службы через локальный канал
└── install / update / uninstall — установка, обновление, откат
```

### 3.1. Служба `omnibox-ai`

Один процесс. Состояние — в памяти:

- **Конфигурация** загружается при старте и после записи. Единственный писатель — сама служба (атомарная замена файла через слой платформы). Читатели получают неизменяемый снимок из памяти, а не с диска, поэтому гонок чтения и записи файлов нет.
- **Контроллер движков** — одна горутина-владелец с очередью команд (start, stop, apply, restore, load, unload, engine-update…). Команды выполняются строго по одной; это заменяет системный mutex управления внутри службы. Желаемое состояние («пользователь остановил») хранится здесь же — основа для F3.
- **Шлюз `/v1`** — reverse proxy на loopback-движок с потоковой передачей SSE. **Очередь генераций (F2)** — канал с ограниченной глубиной и таймаутом. Допуск в генерацию и команды контроллера связаны «поколением»: смена модели, stop, обновление увеличивают поколение, и запросы прежнего поколения в очереди завершаются ошибкой, не попадая на другую модель.
- **Учёт генерации** — перенос логики `Inference.Stats.cs`: usage из JSON/SSE, журнал `requests.jsonl` с ротацией, необязательный `content.jsonl`.
- **Панель** — те же маршруты; сессии, CSRF, проверка Origin/Host, PBKDF2, блокировка после ошибок, доверие `X-Forwarded-*` только от `trusted_proxy_addresses`.
- **Телеметрия** — только по запросу открытой вкладки (см. раздел 6).

Все HTTP-обработчики асинхронны, долгие операции идут в горутинах; блокирующего главного потока (F1) в этой модели нет по построению.

### 3.2. Движки — отдельные службы

Каждый движок остаётся **отдельной службой ОС**, которую запускает тот же бинарник в режиме `engine --profile <xml>`:

- движок переживает перезапуск и обновление панели, текущая генерация при обновлении панели не обрывается;
- Windows: SCM + Job Object на дерево процессов (как `Service.Host.exe` сейчас); Linux: unit systemd с `KillMode=control-group`;
- хост пишет журналы с ротацией и `runtime.json`, как сейчас.

Альтернатива — запускать движки дочерними процессами службы — проще, но обновление панели обрывало бы генерацию и останавливало модель. Отклонена.

### 3.3. CLI `ai` — клиент службы

`ai status`, `ai start`, `ai context` и т. д. отправляют команды службе через локальный канал (Windows: именованный канал с ACL «SYSTEM и администраторы»; Linux: unix-сокет с правами 0660 для группы `omnibox`). CLI больше не редактирует файлы сам, поэтому межпроцессных гонок CLI и панели нет, а замок `Global\omnibox-ai-control-v1` внутри новой версии не нужен.

Если служба не запущена, CLI умеет только диагностику, запуск службы и `install`/`update`.

## 4. Структура репозитория

```
go.mod, go.sum
cmd/omnibox/            точка входа, разбор режимов и команд
internal/config/        config.json: схема, проверка, атомарная запись, профили движков с откатом
internal/engine/        адаптеры PrismML и Ollama: аргументы, готовность, модели, размещение
internal/control/       контроллер: эксклюзивность, применение и откат, поколения, желаемое состояние
internal/gateway/       /v1: авторизация, очередь, прокси, usage, журналы запросов
internal/panel/         HTTP API панели, сессии, CSRF, безопасность, статика (embed web/)
internal/telemetry/     CPU, RAM, диски, GPU, температуры — по запросу
internal/storage/       объёмы, срок хранения, очистка
internal/enginemgr/     версии движков из GitHub, установка, удаление
internal/catalog/       Hugging Face, скачивание GGUF с докачкой (F4)
internal/update/        самообновление из GitHub Releases, откат
internal/platform/      интерфейсы ОС и реализации *_windows.go / *_linux.go
web/                    интерфейс без изменений
tests/                  http_test.py, web_test.cjs и Go-тесты интеграции
```

PowerShell-версия (`src/`, `install.ps1`, `dist/`) остаётся в репозитории до завершения перехода и получает только исправления ошибок.

## 5. Слой платформы и сборка под Linux

Всё, что зависит от ОС, — за интерфейсами в `internal/platform`; остальной код общий.

| Интерфейс | Windows | Linux |
|---|---|---|
| Службы | SCM через `golang.org/x/sys/windows/svc/mgr` | systemd: unit-файлы и `systemctl` |
| Хост службы | `x/sys/windows/svc` | обычный процесс под systemd, `sd_notify` |
| Дерево процессов движка | Job Object (`KILL_ON_JOB_CLOSE`) | cgroup unit-а (`KillMode=control-group`) |
| Секреты (сессии, доступ к GitHub) | DPAPI LocalMachine — тот же формат, что `panel-sessions.dpapi` | файл 0600 владельца службы |
| Атомарная замена файла | `ReplaceFileW`, совместимо с открытыми читателями | `rename(2)` |
| Права каталога | ACL: SYSTEM, администраторы, владелец | владелец `omnibox`, 0750 |
| Firewall | правило Windows Firewall для порта | не трогаем (настраивает владелец) |
| Локальный канал CLI | именованный канал с ACL | unix-сокет |
| Пути по умолчанию | программа `C:\Program Files\OmniBox AI`, данные `C:\ProgramData\OmniBox AI` | `/opt/omnibox`, данные `/var/lib/omnibox`, журналы `/var/log/omnibox` |

Сборка: CI собирает `GOOS=windows` и `GOOS=linux` на каждом коммите (`CGO_ENABLED=0`, статические файлы). Код для одной ОС, сломавший сборку другой, не пройдёт CI. Под WSL2 работает тот же Linux-бинарник.

## 6. Мониторинг

Опрос — только по запросу открытой вкладки, как сейчас; источники становятся полнее:

| Данные | Windows | Linux | Как |
|---|---|---|---|
| CPU (общая и по ядрам), RAM, swap, диски, сеть, процессы движка | да | да | `gopsutil` |
| GPU: загрузка, VRAM, температура, мощность, частоты, вентилятор, память по процессам | да | да | NVML (`nvml.dll` / `libnvidia-ml.so`) без cgo; запасной путь — `nvidia-smi` |
| Температура CPU | только с внешним компонентом | да (`hwmon`) | см. ниже |
| SMART и температура дисков | опционально | опционально | `smartctl`, если установлен |

**Температура CPU на Windows** не имеет штатного API для пользовательских программ: нужен драйвер ядра. Старый драйвер WinRing0, который использовали LibreHardwareMonitor и подобные программы, Microsoft Defender блокирует как уязвимый. Решение владельца: необязательная интеграция с LibreHardwareMonitor, который владелец устанавливает сам; OmniBox читает его локальный веб-сервер (JSON) только по запросу открытой вкладки. Без него панель показывает «—» и подсказку. Сам OmniBox драйверов не ставит.

## 7. Зависимости

Правило смягчено (см. `AGENTS.md`):

- Go-модули разрешены при лицензии MIT, BSD или Apache-2.0, с версиями в `go.sum`, без cgo. Каждая новая зависимость указывается в PR с причиной.
- Ядро — один бинарник: на ПК для работы OmniBox ничего ставить не нужно.
- Python, Node.js и другие программы на ПК допустимы для **необязательных** возможностей (например, мониторинг через внешний компонент или будущий движок), если панель без них работает и явно показывает, что компонент не установлен.
- В вебе по-прежнему без CDN: шрифты и картинки локально.

Ожидаемые зависимости первой версии: `golang.org/x/sys` (BSD-3), `github.com/shirou/gopsutil` (BSD-3), загрузка NVML без cgo (`github.com/ebitengine/purego`, Apache-2.0) — окончательный список фиксируется в PR каждого этапа.

## 8. Установка, обновление и выпуски

- **Выпуски — GitHub Releases** (закрывает E3): `omnibox-windows-amd64.zip`, `omnibox-linux-amd64.tar.gz` и `SHA256SUMS`. `dist/` в `main` больше не нужен после перехода.
- **Установка и обновление одной командой** (требование владельца). Один скрипт-загрузчик для обоих случаев:
  - Windows: `install.ps1` работает и во встроенном Windows PowerShell 5.1, поэтому PowerShell 7 больше не нужен. Запуск одной строкой, как сейчас: через `gh` (репозиторий закрытый) скачивается загрузчик, он скачивает последний выпуск (или указанную версию), сверяет SHA256 и запускает `omnibox install`. Если OmniBox уже установлен, та же строка обновляет его с сохранением всех настроек;
  - Linux и WSL2: `install.sh` с тем же поведением;
  - без `gh` — одноразовый токен GitHub, который запрашивается в память и не сохраняется в журналах;
  - после установки обновление также доступно как `ai update` и кнопкой в панели; все три пути выполняют одну и ту же процедуру.
- **`omnibox install`** — из распакованного выпуска: копирует файлы в `bin\<версия>`, регистрирует или переключает службы на новый путь, сохраняет предыдущую версию для отката. Транзакция с журналом и откатом, как в `Install.Transaction.psm1`: снимок, шаги, автоматический откат, сверка настроек по значениям.
- **Обновление** из панели и `ai update` — служба скачивает выпуск, проверяет SHA256 и запускает установщик из новой версии отдельной временной службой (как `update-worker`), чтобы замена панели не обрывала процесс обновления.
- **Переход с PowerShell-версии** — чистая установка той же одной командой; старые службы удаляются по подтверждению (раздел 2.2), их файлы остаются на диске.
- **Подпись бинарника** — решение владельца: подписывать. Подпись выполняется в CI секретом репозитория; варианты сертификата (облачная подпись или OV-сертификат) владелец выбирает до этапа D. Пока сертификата нет, выпуски не подписаны, и шаг подписи пропускается с предупреждением.

## 9. Этапы перехода

Каждый этап — отдельные PR с CI на Windows и Linux. PowerShell-версия до этапа D остаётся рабочей версией на ПК. По решению владельца параллельный запуск двух панелей не нужен: переход полный, а если с Go-версией возникнет серьёзная проблема, ставится прежний выпуск (`releases.json`, git).

**Этап A — каркас и чтение.** Модули `config`, `profile`, `platform`, `panel` (вход, сессии, статика), `/api/status`, `/api/telemetry`, журналы.
Готово, когда: маршруты чтения отвечают в формате PowerShell-версии (тот же JSON для `web/app.js`), `web_test.cjs` проходит; потребление памяти в простое измерено.

**Этап B — управление и `/v1`.** Контроллер с откатом профиля и поколениями, режим `engine` вместо `Service.Host.exe`, шлюз `/v1` с очередью F2 и учётом генерации.
Готово, когда: проходят все HTTP-тесты управления и шлюза; тесты очереди: порядок, таймаут, отмена при отключении клиента, сброс поколения при stop/unload/apply/update; реальные SCM-тесты в Windows CI.

**Этап C — остальные возможности.** Менеджер движков, хранение и очистка, каталог и скачивание с докачкой (F4/F5), обновление, мониторинг (раздел 6).
Готово, когда: все функции PowerShell-версии доступны в Go-версии; тесты на каждую.

**Этап D — установщик и переход.** `omnibox install/update` с мастером по умолчанию, CLI `ai`. Проверка на одноразовой Windows-машине CI: чистая установка одними Enter, удаление старых служб, обновление с сохранением настроек, сбой на каждом шаге и откат.
Готово, когда: владелец обновил ПК, панель и клиенты работают; через одну стабильную версию PowerShell-код удаляется из репозитория.

**Этап E — Linux.** Unit-файлы systemd, установка в `/opt/omnibox`, движки PrismML и Ollama для Linux, проверка под WSL2.
Готово, когда: CI собирает и тестирует Linux-версию с настоящим systemd в контейнере или VM; описана установка на Linux и в WSL2.

Задачи плана F2, F3, F4, F5, F7, F8, S1–S3 реализуются в Go-версии на соответствующих этапах и в PowerShell-версии не делаются.

## 10. Риски

| Риск | Мера |
|---|---|
| Регрессии при переписывании | Тот же JSON-контракт для `web/app.js`, перенос проверок из нынешних тестов в Go-тесты; откат на прежний выпуск |
| Миграция ломает установку | Транзакционный установщик с откатом, проверка перехода в Windows CI на реальной машине |
| Неподписанный exe и антивирусы | Подпись кода (решение владельца), сборка без упаковщиков |
| Параллельная поддержка двух версий | PowerShell-версия — только исправления ошибок, новые возможности — только в Go |
| Различия Windows и Linux | Слой платформы, сборка обеих ОС в CI на каждом коммите |

## 11. Решения владельца

1. Движки — отдельные службы, запускаемые тем же бинарником (раздел 3.2).
2. CLI `ai` — клиент службы через локальный канал (раздел 3.3).
3. Бинарник подписывается; сертификат выбирается до этапа D (раздел 8).
4. Температура CPU на Windows — через необязательный LibreHardwareMonitor (раздел 6).
5. Нумерация продолжается: Go-версия выходит следующим номером по порядку (0.x), а не 1.0.0 — до релиза ещё далеко.
6. Установка и обновление — одной командой, одинаковой для нового ПК и для уже установленной программы (раздел 8).
7. Без параллельного запуска двух панелей: полный переход на Go-версию; при серьёзной проблеме — установка прежнего выпуска.
8. Без наследия: один `config.json` нового формата, профили движков в JSON со структурированными настройками, новые имена служб и каталоги, один порт (раздел 2).
9. Чистая установка без переноса данных PowerShell-версии; мастер установки проходится одними Enter — у каждого вопроса есть ответ по умолчанию.
